# AGENTS.md — правила работы над Archon Universe

Файл обязателен к прочтению для **любого** AI-агента (и человека) перед любой правкой. Он не привязан к поставщику моделей: подходит для OpenRouter, Ollama, локальных и облачных моделей, любых OpenAI-compatible API и CLI-агентов.

## Направление проекта

Это личная студия владельца для развития связной вселенной, историй, прозы и сценариев совместно с агентами; публичная витрина не является основным сценарием. Прорабатывай сферы комплексно, отмечай последствия, зависимости и противоречия, но не выдавай гипотезы или черновики сцен за канон. `drafts/concepts/`, `drafts/stories/catalog.json`, `drafts/diaries/` и `drafts/works/` видны на сайте и не являются приватным хранилищем; правила историй и сцен описаны в `drafts/stories/README.md`. См. `ROADMAP.md` и `/studio`.

## 0. Золотые правила

1. **Источник истины — `universe/`** (Markdown + YAML). Не создавай копий лора в коде, JSON, БД, сайте или игре.
2. **Не выдумывай канон.** Нет сведений → пиши `—` и добавляй пункт в «Противоречия и неизвестные сведения» или в [`Открытые вопросы`](universe/00-meta/Открытые%20вопросы.md). Не заполняй пустые разделы «для красоты».
3. **Не утверждай канон сам.** Статус `canon` ставит только человек-владелец. Агент максимум предлагает `proposed`/`review`.
4. **Новые идеи — в `drafts/`**, не в `universe/`.
5. **Не удаляй и не переписывай** чужое целиком. Делай локальные правки; удаление — только по согласованию (вместо удаления — `deprecated`/`archived`).
6. **Гипотеза ≠ факт.** Любое «предположительно/возможно» из источника остаётся оговоркой и не превращается в утверждение.
7. **Не меняй художественный стиль** (визуальный, звуковой) без согласования.
8. **Не смешивай лор и игровые механики.** Характеристики, баланс, классы — в Game Data, не в статьях.
9. **Не создавай технологии, локации, персонажей** только чтобы заполнить пустой раздел.
10. **Научная достоверность:** никакой магии и произвольных нарушений физики. Необъяснимое помечай как неизвестное (`science_status: unexplained`).

## 1. Перед созданием/изменением сущности

1. Прочитай [`Правила канона`](universe/00-meta/Правила%20канона.md) и [`docs/worldbuilding/ENTITY-GUIDE.md`](docs/worldbuilding/ENTITY-GUIDE.md).
2. **Найди дубликаты**: поиск по `id`, `title`, `aliases` (`grep -ri "<имя>" universe drafts`; `npx tsx scripts/lore.ts index` → `build/lore/index.json`).
3. Проверь связанные сущности и их статусы; отметь противоречия.
4. **Сохраняй ID.** ID постоянен: не переименовывай, даже если меняется название или файл.
5. Бери шаблон из `templates/`. Даты `created`/`updated` — сегодняшние (`YYYY-MM-DD`).
6. Укажи источник в разделе «Источники».

## 2. Перед коммитом (обязательно)

```bash
npx tsx scripts/lore.ts validate   # 0 ошибок обязательно
npx tsx scripts/lore.ts report     # посмотри новые противоречия
npx vitest run
npx tsc --noEmit
```

Автоматические проверки **никогда** не изменяют канон. Не «чини» валидатор, подгоняя данные под него, и не ослабляй проверки ради зелёного CI.

## 3. Процесс изменений

Задача → изучение существующих материалов → план → **черновик** (`drafts/`) → проверка другим агентом (Continuity Auditor) → проверка человеком → Pull Request → утверждение → слияние.

- Крупные изменения веди в рабочей ветке, назначенной для текущей задачи; соблюдай правила окружения о ветках.
- Агент **не сливает** спорные изменения в канон и не мержит собственные PR, затрагивающие `universe/`.
- Изменения канона записываются в `CHANGELOG.md`.

## 4. Структура проекта (кратко)

```
universe/   база лора     templates/  шаблоны      drafts/   идеи (concepts/ публичны как черновики)
packages/   lore-schema · lore-parser · lore-validator · lore-indexer
scripts/lore.ts  CLI     src/  энциклопедия (Next.js)     docs/  документация и ADR
```

Подробности: [`ARCHITECTURE.md`](ARCHITECTURE.md). Не создавай пустых директорий и абстрактных модулей «на будущее». Архитектурные решения фиксируй в `docs/decisions/` (ADR).

## 5. Статусы сущностей (кратко)

`draft` → `proposed` → `review` → `canon`; `deprecated` (устарело, есть замена), `archived` (исторический материал), `unresolved` (известно, что есть, но суть требует уточнения). Полная семантика — в «Правилах канона».

## 6. Роли

Lore Architect · Worldbuilding Agent · Continuity Auditor · Science Research Agent · Art Director Agent · Software Engineer · Documentation Agent.
Зоны ответственности, входы/выходы и промпты-чеклисты: [`docs/agent-workflows/ROLES.md`](docs/agent-workflows/ROLES.md).

## 7. Код

- TypeScript strict, Zod для схем. Новые зависимости — только при реальной необходимости, без платных.
- Логика знаний — в `packages/*` без зависимости от Next.js/Obsidian. Приложения только читают.
- Новый тип сущности/связи → `packages/lore-schema` + шаблон + тест.
- Не требуй сервера для базовой работы; всё должно собираться статически.
- Секреты — только через `process.env`, не в репозитории.
- При изменениях сайта запускай `npm run lint`, `npm run typecheck`, `npm test`, `npm run test:e2e` и `npm run test:e2e:dev`; проверяй узкие телефоны, горизонтальную ориентацию, планшеты и широкие экраны, а также навигацию с клавиатуры. Смотри скриншоты, не обновляй визуальные эталоны без проверки. Dev- и production-проверки обе важны: превью может отдавать устаревший CSS. Браузерные тесты используют `@sparticuz/chromium`; локальные артефакты отчётов не коммить.
- Граф лора строится только из опубликованных сущностей и их связей; карта гипотез отдельно и не утверждает их как факты. Поле `ID обязательных зависимостей` в каждой гипотезе обновляй вместе с её текстом; другие упоминания ID, включая отрицания, не являются зависимостью. В `ID записей архива` указывай только опубликованные тематические точки входа; указатель не добавляет связь в лор, списки не ссылаются на неопубликованные записи. Вся папка `drafts/concepts/` публична, включая текстовые ID. Табличное представление и управление с клавиатуры сохраняй.
- Публикуемая мастерская читает `drafts/concepts/`; не помещай туда приватный контент. У концепт-арта фиксируй происхождение, права и точный промпт. Поисковый индекс публикует только опубликованные записи, публичные гипотезы и концепции и каталог арта; прочие drafts и скрытые сущности в него не включать. Текст статей индексируй после публичного рендеринга и санитаризации, без frontmatter и адресов скрытых ссылок. Результаты мастерской явно отделяй от лора.

## 8. Проактивная разработка мира и гипотезы

Владелец поручил агенту самостоятельно предлагать развитие мира, не выдавая предложения за утверждённые сведения. Новые гипотезы фиксируются в `drafts/` и не публикуются как лор.

- Дай каждой гипотезе постоянный уникальный ID `H-###`; не переназначай ID даже после отклонения или изменения идеи.
- Указывай статус, исходные решения владельца и связанные сущности, обязательные зависимости от других гипотез, последствия, ограничения и вопросы проверки. Отделяй обязательные зависимости от необязательных связей.
- Фиксируй ответы владельца по ID: «нравится», «не нравится», «доработать». Положительная оценка одной гипотезы не означает принятия её зависимостей, следствий или статуса `canon`.
- Если принятое предложение зависит от спорного или отклонённого, отметь это и предложи новую редакцию; не удаляй историю и не исправляй противоречие догадкой.
- Подготовка к переносу в `universe/` — отдельная проверка человеком и PR; `canon` утверждает только владелец. Соблюдай ограничения: нейроинтерфейсы исключены из действующей основы, биологические вычисления рассматриваются самостоятельно, Лимб использует внешнее VR-оборудование.

## 9. Если не уверен

Для предположений предлагай гипотезу в `drafts/`; нерешённые вопросы и противоречия явно фиксируй. Не превращай догадку в факт.

Публичные концепции могут явно указать `**ID упомянутых гипотез:** H-022, H-023` (или `нет`): это создаёт обратные указатели на страницах гипотез, но не означает зависимости или принятия. Указывай только существующие ID; приватные черновики в эти указатели не включаются.

Для явно несовместимых гипотез указывай взаимное поле `**ID несовместимых гипотез:** H-...` с обеих сторон и описывай границы конфликта в тексте. Не выводи несовместимость автоматически из упоминания; предупреждение в черновиках не заменяет решения владельца.
